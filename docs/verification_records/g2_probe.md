# G2 structured-output capability probe

## Purpose and decision

Stage D generation under `generation-frozen-G` stopped after the repaired
assignment prompt produced an out-of-list cluster ID on a second formal
dataset. The standing trigger established when that prompt repair was closed
required the JSON Schema decision to reopen.

The proposed G2 instrument could proceed only if all three formal model
configurations accepted the same constrained assignment schema through their
production provider path. The live capability gate passed for all three
models. This result authorised implementation work; it did not create or
approve the G2 tag.

## Interpretation limit

A schema-valid answer to one adversarial request cannot prove with certainty
that an endpoint enforced the schema rather than the model independently
complying. The adversarial illegal-ID instruction makes that false-positive
route less likely but does not eliminate it. G2 therefore retains the local
strict parser and legal-ID validation as a second gate. Any later invalid,
empty, refused, filtered, or timed-out response still fails the run without
partial cluster persistence.

Microsoft's published structured-output support list did not name
`Mistral-Large-3`, while the configured Azure deployment accepted and obeyed
the strict schema request in this probe. The capability claim is therefore
limited to this recorded deployment and request, not generalised to all
Mistral or Azure deployments.

## Safe rerun

Daily tests:

```powershell
cd ai-service
.\venv\Scripts\python.exe -m unittest tests.test_g2_schema_probe -v
```

Explicit manual live mode:

```powershell
cd ai-service
.\venv\Scripts\python.exe tools\g2_schema_probe.py --live --model all
```

Live mode is never enabled by ordinary `unittest discover`. It requires
operator intent, valid local provider configuration, and the same secret
handling rules as formal generation.
